2安全網を最初に張る ── Gitと小さなコミット

直せる人がいちばん最初にやるのは、コードを書くことではありません。 「いつでも、壊れる前に戻れる」状態を作ることです。これがあると、思い切って試せます。 失敗が怖くなくなります。バイブコーディングにおいて、Gitは技術ではなく勇気の源です。

なぜGitが「自己修正」の土台なのか

バイブコーディングでは、AIが一度に大量のコードを書き換えます。 うまくいけば最高ですが、失敗すると「さっきまで動いていたのに、何が変わったのか分からない」状態に陥ります。 Gitがあれば、この問いに一瞬で答えられます ── 「直前から、ここが、こう変わった」。そして、嫌なら一行のコマンドで巻き戻せます。

Gitなしで起きる悲劇 動いていた状態を保存せずにAIに大改造させ、壊れ、元に戻せず、何時間も溶かす。 バイブコーディング最大の事故はこれです。逆に言えば、Gitさえあれば、この事故は原理的に起こりません。

覚えるのはこの5コマンドだけ

Gitには何百もの機能がありますが、自己修正の安全網として必要なのは、最初は次の5つだけです。

# ① 最初の一度だけ：このフォルダをGit管理下にする
git init

# ② 今の状態を「保存候補」に入れる（全ファイル）
git add -A

# ③ 保存する（セーブポイントを作る）。-m の後ろは自分用のメモ
git commit -m "ログイン画面が動くところまで"

# ④ 今、前回の保存から何が変わったかを見る
git diff

# ⑤ 【最強の戻る】保存以降の変更を全部捨て、直近の保存状態に戻す
git restore .        # 追跡中ファイルの変更を破棄
git checkout -- .    # 古いGitでの同等コマンド
コミット＝ゲームのセーブポイント git commit は、RPGのセーブと同じです。ボス（難しい機能）に挑む前にセーブする。 全滅（コード崩壊）したら、ロード（戻す）してやり直す。「動いた」と思った瞬間が、セーブのタイミングです。

黄金ルール：「動いたら、すぐコミット」

バイブコーディングでの鉄則はたった一つ。小さく動くものができるたびに、すぐコミットすること。 1日の終わりにまとめてではなく、「ボタンが表示された」「保存ができた」レベルで、こまめに。 こうすると、いつ壊れても「直前の動く状態」がすぐ隣にあります。

タイミングやること
新しい機能に手をつける前今の動く状態をコミット（避難先を確保）
AIに大きな変更を頼む前コミット（巻き戻し地点を作る）
小さな機能が1つ動いたすぐコミット（成果を確定）
壊れて、原因が分からなくなったgit restore . で直近コミットへ撤退

事故ったときの「撤退」手順

AIにあれこれ頼んだ結果、何が何だか分からなくなった。よくあります。落ち着いて次を実行してください。

  • まず差分を見る： git diff で「保存後に何が変わったか」を確認。原因が見えることも多い。
  • 戻すと決めたら： git restore .（または git checkout -- .）で、直近コミットの状態に全部戻す。
  • 動くことを確認： 戻った状態でプログラムを動かし、確かに直っているか見る。
  • 仕切り直す： さっきは一度に頼みすぎた、と反省し、今度はもっと小さく刻んで頼む（第9章）。
この章の核 コードを書く前に、まず git init → git commit で安全網を張る。 「動いたらコミット」を口癖にする。壊れたら git restore . で戻る。
これだけで、バイブコーディング最大の事故が消える。
