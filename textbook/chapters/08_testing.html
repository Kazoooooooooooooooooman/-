7検証とテスト ── 「動いた」を証明する

バイブコーディング最大の落とし穴は、「動いたつもり」です。AIが「できました」と言い、 画面が一度それらしく動いた ── それだけで完成にすると、後で必ず痛い目を見ます。 直せる人は「動いた」を証明します。この章は、その証明のやり方を、軽いものから順に渡します。

検証の3階層 ── まずは一番下でいい

階層やり方いつ使う
① 目視確認自分で操作して、目で見て確かめる常に。最低限これは必ず
② 境界の確認「変な入力」でも壊れないか試す機能が一通り動いたら
③ 自動テスト確認をコード化し、毎回自動で回す同じ確認を繰り返すなら

最初は①だけで十分です。慣れてきたら②、繰り返しが増えてきたら③へ。背伸びは不要です。

① 目視確認 ── ただし「正常系」で満足しない

ほとんどの人は、うまくいくケース（正常系）だけ試して安心します。 しかしバグは、たいていうまくいかないケースに潜んでいます。最低限、次の3パターンは触ってください。

  • 正常： 普通に正しく使う（例：正しいメールで登録）
  • 空： 何も入れずに実行（例：空欄のまま送信）
  • 変： 想定外を入れる（例：メール欄に「あ」、数量にマイナス）
「壊し方」チェックリスト（汎用）
  • 入力を空のまま実行したら？
  • とても長い文字や絵文字を入れたら？
  • 数字の欄に文字、マイナス、0、巨大な数を入れたら？
  • 同じボタンを連打したら？　二重に登録されない？
  • 途中で戻る・リロードしたら？　データは壊れない？

② 境界値 ── バグは「端っこ」に住む

不具合が集まる場所は決まっています。境目です。 「18歳以上OK」なら、17・18・19歳。「10件まで」なら、9・10・11件目。 ちょうどの値とその前後を試すと、> と >= の取り違えのような典型バグが面白いほど見つかります。

③ 自動テスト ── 「確認」を未来の自分に贈る

同じ手動確認を何度も繰り返すなら、それをコードにしておくと、毎回ボタン一つで確認できます。 これが自動テストです。難しく考えず、「この入力なら、この結果になるはず」を書くだけです。 

# 例：税込価格を計算する関数 calc_tax をテストする（Python）
def test_calc_tax():
    assert calc_tax(100) == 110      # 100円 → 110円のはず
    assert calc_tax(0)   == 0        # 0円 → 0円のはず（端っこ）
    assert calc_tax(1)   == 1        # 端数の丸めも確認

assert A == B は「AがBでなければ、そこで止まって教えて」という意味。 これを書いておけば、後でAIにコードを改造させた後でも、壊れていないか一瞬で分かります。 バイブコーディングと自動テストは、実はとても相性が良いのです。

AIにテストを書かせる テストの書き方が分からなければ、こう頼みます ── 「この関数のテストを書いて。正常系・空・異常系・境界値を含めて」。 さらに「テストを先に書いて、それが通るように実装して」と頼むと、品質がぐっと安定します。

「直った」を確認する ── 回帰チェック

バグを直したときは、2つを必ず確認します。①本当にそのバグが消えたか。 そして見落としがちな②別の場所を壊していないか。AIの修正は、しばしば関係ない所に副作用を出します。 直したら、周辺の機能も一通り触り直す ── これを回帰チェックと呼びます。自動テストがあれば、これが一瞬で済みます。

「たぶん動く」を完成にしない 動作を一度も自分で確認せずに「完成」「デプロイ」するのは、最も多い後悔の原因です。 AIの「できました」は報告であって、保証ではありません。最後に動かすのは、いつもあなた。
この章の核 「動いたつもり」を証明に変える。最低限正常・空・変の3パターンを試す。 バグは境界に住む。繰り返す確認は自動テスト化する。直したら回帰チェックで副作用を見る。

章末チェック

  • 正常系だけでなく、空・異常・境界値も試している
  • 「壊し方チェックリスト」で意地悪な入力を試せる
  • 簡単な assert テストを書ける（またはAIに書かせられる）
  • バグ修正後に「別の場所を壊していないか」確認している
  • 自分で動作確認するまで「完成」と言わないと決めた
